# v0.4 Phase 2 — the retail health cheat and callback `0x002D2620` — 2026-10-22

Target: *The SpongeBob SquarePants Movie* (USA), PS2 `SLUS_209.04`,
SHA-256 `2ff117f45e80be5e2d73b6c952f4b5adfb8d359c8cc6c14eb5906197994ce956`.
Method: static disassembly plus targeted cross-reference scans of the retail
ELF (same method as the Phase 1 trace,
`docs/V0.4-PS2-CHEAT-TRACE-2026-10-22.md`). Question posed for this phase:
does the existing retail "all six health slots" cheat already exercise its
callback correctly, and what exactly does the callback do to health, slots,
the HUD, and save data?

**Short answer: yes, the retail cheat is complete and correct. No new patch
was created in this phase** — testing and tracing revealed no missing feature
worth adding (see the verdict at the end).

## The cheat record (recap, from the Phase 1 trace)

`cheatList[1]` at `0x005FBCC0`: key array `0x005FBB70`, callback `0x002D2620`,
`flg_keep 0x00000100`, `flg_mode 0` (add/OR). Sequence (paused, hold
L1+L2+R1+R2): **Circle Circle Circle Circle Square Circle Square Circle** —
identical to the published retail code for "Unlocks all six health slots".
The handler path that reaches the callback (append → compare → flag OR →
`jalr` at `0x002D2974`) was hardware-validated in Phase 1 via record 8.

## What the callback at `0x002D2620`–`0x002D2730` does

In order (all addresses are instruction addresses in the retail ELF):

1. **Grants maximum health slots to both characters.**
   `0x002D2634`: `*(u32*)0x007AC084 = 6`; `0x002D2638`:
   `*(u32*)0x007AC4F4 = 6`. These are the two per-character health-slot counts
   (the two player state blocks sit 0x470 apart).
2. **Sets the persistent bonus-slot bytes.**
   `0x002D2644`: `*(u8*)0x007ABC01 = 3`; `0x002D264C`:
   `*(u8*)0x007ABC02 = 3`. See the state model below: slots = 3 + bonus, so
   bonus 3 is the maximum.
3. **Refreshes the unlockables UI table.** Loop `0x002D2650`–`0x002D26CC`
   over the 0x10-stride table at `0x005FC510` (count at `0x00636528`):
   each entry whose fields 0 and 8 both equal 10 gets its display-state
   halfword (object pointer at entry+0xC, halfword at object+0x14) rewritten
   from the shared UI-state halfword at `0x007ACFE8`; other entries get a
   byte-sourced state from `0x007ABBF9 + *(u32*)(entry+8)`. This is the
   same commit-to-UI helper pattern the two move-cheat callbacks use.
4. **Conditionally refreshes the pause/powerup UI flow.** `0x002D26D0`–`0x002D2718`: hashes the flow
   name `"PAUSESTATE MENU OR POWERUP COUNTER"` (`0x0061FEC4`), looks the flow object up
   (`0x002EED90`); if the object exists and its state halfword at +0x14 equals 2,
   it triggers the flow via `0x003EB940` with the UI manager global at
   `0x0063652C` and argument `0x3C` (60). The UI function body and its visible
   effects are not executed by the callback simulation.

What it does **not** do: it never writes any current-HP variable (the live HP
value read by the HealthMenu tooling, reached via the pointer at
`0x007ABC10` + 0x460, is untouched). The cheat raises the **maximum** slots;
it does not refill health. That matches its published name — a slots unlock,
not a heal.

## The health-slot state model (traced from the other writers/readers)

| Address | Role |
| --- | --- |
| `0x007ABC01` / `0x007ABC02` | Per-character **bonus-slot bytes** (0–3). They are entries 8 and 9 of the serialized unlock-state byte array based at `0x007ABBF9`. |
| `0x007AC084` / `0x007AC4F4` | Per-character **slot counts** = 3 + bonus. Written by the callback, by the load derivation, and by the reset function. |
| `0x007AC080` / `0x007AC4F0` | Shadow copies of the slot counts, synced by the helper at `0x0034EE40` (the HUD/display layer works from these). |

- **Defaults:** the reset/init function at `0x0034EE70` writes 3 to both slot
  counts, both shadows, and the related counters — a new game starts with 3
  health slots per character.
- **Load derivation (confirmed):** the game-load function reads the unlock
  byte array from the save via the serializer (`0x00460730`, loop at
  `0x002F3780`), then derives the slot counts: `0x002F37A4`–`0x002F37C4`
  computes `slotA = byte[0x7ABC01] + 3`, `slotB = byte[0x7ABC02] + 3`, stores
  them, and calls the shadow-sync helper `0x0034EE40`. The callback is
  **not** re-run on load — its effect is re-applied by this derivation.
- The only other writers of the slot words are the callback, this load path,
  and the reset function — the state stays consistent by construction.

## Save-data effects (two independent channels, both confirmed)

1. **The bonus-slot bytes are serialized game state.** The load function
   reads them out of the save's unlock block, so the cheat's grant persists
   exactly like a legitimately collected slot upgrade. (Load side verified
   instruction-by-instruction; the save side writes the same array in the
   save routine that also calls `zGameExtras_Save` at `0x002F3E68`.)
2. **The cheat flag persists too.** Record 1's bit `0x100` lies inside the
   low 16 bits that `zGameExtras_Save` (`0x002D2AB0`) writes, and
   `zGameExtras_Load` ORs it back in — unlike record 8's costume bit
   (`0x10000000`), which is deliberately outside the saved range.

## Verdict

The retail cheat exercises the callback completely and correctly: the
handler reaches it through the same hardware-proven path as Phase 1, the
callback updates both characters' persistent bonus bytes *and* their derived
slot counts, refreshes the unlockables UI, syncs through the same shadow
mechanism the rest of the game uses, conditionally calls the UI-refresh flow, and leaves
state that the load path reconstructs faithfully. Current HP is intentionally
not refilled — that is the retail design, and the decomp-era name for this
slot (`MaxHealthSlotsCB`) agrees.

**No experimental patch was created in Phase 2.** The only conceivable
"addition" — making the cheat also refill current HP — would change the
meaning of a retail cheat rather than restore or complete anything, so it
fails the phase's own test ("a specific feature worth adding"). If that is
ever wanted as an explicit experiment, it is a one-word callback change and
can be built on this trace; it is not part of Phase 2.

## Owner confirmation test (retail behavior, no patch involved)

On the retail ISO (already in the PS3's PS2ISO), or any ISO with an
unmodified cheat table:

1. Start a level; note the health display (3 slots).
2. Press Start to pause, hold L1+L2+R1+R2, enter
   **Circle ×4, Square, Circle, Square, Circle**.
3. Predictions from the trace: step jingles during entry, the success
   jingle and the health display grows to **6 slots**;
   current HP value itself does not refill.
4. Save, reboot, reload: slots stay at 6 (bonus bytes + flag both persist).
